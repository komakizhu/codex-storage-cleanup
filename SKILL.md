# Codex 存储清理（Codex Storage Cleanup）

Use this skill as the standalone entry point for a Codex storage check and its scoped default cleanup. It includes its own scanner, cleanup executor, daily entry, report builder, bounded process helper, and visual theme; it does not read files from another Skill. Reports and daily history default to `/Users/mac/.codex/skill-workspaces/codex-storage-cleanup`. Before scanning or acting, confirm the executing account and home through the system account database; operate only on that account. Read [the full SOP](references/codex-storage-cleanup-sop.md) before inspecting or proposing a concrete operation. For T1 snapshots or account-specific operations, also read [the vault operations reference](references/t1-vault-operations.md) and inspect `python3 scripts/vault.py --help`. Vault paths are derived from the executing account's home; the cleanup executor independently verifies the requested home. Preserve each workspace and worktree root.

## Default recommendation: old local artifacts first

Give a clear recommendation, not just a disk inventory or “please decide”. Prioritize large obsolete build outputs in confirmed Documents/Codex and Documents/ChatGPT workspaces, then confirmed worktrees. Within that class, rank by recoverable space. Preserve workspace roots and source projects.

- During scanning, establish that each complete output directory is generated by an available source project and its build configuration. Check source entrypoints, local workspace members, project output rules and actual compiler/framework output markers. Once established, classify redundant directories as **recommended for deletion**, not generic “large old artifact candidates”. Show their total size prominently.
- Keep one latest completed build directory per user/project, plus anything currently in use or explicitly pinned. Use output timestamps and completed executable/library/framework outputs to select it. Branch, commit, debug/release or architecture differences do not by themselves require extra retained copies: their source is preserved and they can be rebuilt. Keep a sole remaining directory; a newer incomplete build does not displace the latest completed one. Record the exact keeper path beside every deletion recommendation.
- Record the available source revision, rebuild command and expected compilation cost. Unknown rebuild duration, absent historical success logs, different branches, and lack of proof of byte-for-byte equivalence are not reasons to defer verified generated outputs. Missing source or mixed user content is a concrete reason to stop that item. Explain any possible missing dependency download; preserve existing download caches. Do not rebuild or download merely to audit storage, and do not claim an actual build passed when only source/configuration was inspected.
- Keep Cargo registry/git download caches, Rust toolchains, package stores, node_modules, Python environments, model downloads and plugin packages by default. “Downloadable again” is a cost, not a cleanup recommendation. Cargo `target` contains compiled outputs: old redundant targets may qualify, but retain the latest useful build and explain the compilation cost; never confuse them with Cargo download caches.
- Old disposable logs and temporary files are secondary. Chats, generated images, reports, attachments and unique exports remain user data unless a specific closed-task marker, retention evidence, and no-reference check qualify one exact path for T1 backup followed by local removal; a similar prompt or the ability to call an API again does not make it a reproducible build output.
- Default advice is “delete these verified older artifacts; keep these latest builds and download caches”. If evidence is missing, identify it and investigate the largest likely artifacts first. Do not substitute cache deletion to inflate the recommended total.

Read SOP §4 and §7 for retention evidence and §8 for the decision table. The scanner performs source/output inspection and retention decisions before computing recommended bytes. For unsupported builders, finish the read-only investigation of the largest directories in the same run; only genuinely missing evidence belongs in “unable to determine”, with the specific missing evidence stated. Report recommended old builds first, then retained builds/download caches, then small secondary cleanup. Editing this skill or running a scan does not itself change user data. When the user asks to run the default cleanup, execute `python3 scripts/apply_cleanup.py --home <current-user-home> --apply`; this is the scoped action boundary for the three policies below and does not require a separate per-item confirmation.

## 默认三类处置

1. **直接删除可再生内容。** 删除已确认属于 Codex 的缓存、编译缓存、带生成标记的中间/转码/索引目录，以及有源码、构建配置和完成产物证据的冗余旧构建目录；同一项目只保留最新完整可用的一份。此类不做备份，因为删除后可以重新生成。下载依赖、Cargo registry/git、工具链、node_modules、虚拟环境、插件包和模型不属于默认直接删除范围。
2. **备份后删除有结束证据的成果。** `archived_sessions` 中按文件 mtime 识别超过 7 天的 `.jsonl` 和 `.jsonl.zst`，以及同时具备结束标记、连续七天无活动、没有受支持引用的独立旧交付物、报告、截图、生成媒体或交接材料，先使用 T1 `user-data`/归档快照并校验，再删除本机精确路径；最近活动、混合目录、仍被引用或证据不完整的内容保留。
3. **移动已定稿或长期闲置的关联 worktree，释放本机空间。** 扫描 Codex 自身的 `~/.codex/worktrees`，也扫描已确认本地项目根目录下 `.worktrees` 中登记的 linked worktree；这些树不再作为主工作区里的普通构建产物重复扫描。定稿只是候选入口，不能覆盖近期活动或未知状态；整个关联组仍须连续超过 168 小时没有文件/目录修改和会话活动，并通过句柄、引用和 Git 登记检查。尚未归档但超过 168 小时无活动的会话不单独阻断迁移。逐条分类实际路径引用：组内路径在副本中修复；组外绝对路径原样保留；组外相对路径在 T1 副本中重定位以保持原目标；旧路径软链接是访问别名，不算项目引用或阻断项。符合条件的 linked worktree 整组移动到 `/Volumes/T1/Agent/archive/storage-observatory/worktrees/<唯一目录>/worktree`。内容校验成功、必要引用修复、Git 登记修复且新旧入口验证通过后，移除本机数据副本，原路径只保留指向 T1 的软链接。连接 T1 后原路径可继续打开、检索、修改及使用 Git；拔盘时入口暂时不可用。公共 Git 元数据继续保留在本机；锁定外置 worktree，防止离线时被 prune。旁边的 `migration.json` 记录原路径、新路径、关联组、提交/状态和迁移阶段。不能用“复制后本机保留”冒充移动。

执行入口默认先重新扫描；不带 `--apply` 只输出计划。每日健康检查仍然只读，不会因为定时检查而触发清理。

移动前复核 Git 状态、提交、所有权、句柄、当前目录、子模块、会话索引和逐条路径引用。干净且有提交只是定稿候选证据，不等于证明任务永久不会再修改；关联组中任一成员近期活跃、打开状态未知或索引覆盖不足都阻止迁移。脏状态、暂存、未跟踪、忽略文件和无 HEAD 不能单独阻止已经证实长期闲置的整组搬移，但必须完整保留并比较搬移前后状态。组外绝对路径不因“在组外”而阻断；组外相对路径须在 T1 副本中重定位；旧路径软链接作为访问别名，不算项目引用或阻断项。只有无法解析的组内引用、无法保留目标语义的链接、主仓库、子模块或已锁定工作树才阻止该组，并报告具体路径及原因。源保留到内容、引用、Git 和旧路径入口验收成功；失败则恢复源和 Git 登记，若断电或清理中断则按迁移记录继续恢复，不把失败计作已释放。复制阶段的临时本机原件不是最终保留策略。

容量汇报必须包括三类：直接删除量、归档和已结束成果备份后删除量、worktree 搬移释放量。按路径、文件身份和硬链接去重；先处理独立可再生项，再重新测量父 worktree 的剩余内容，不能重复计算内部构建。已迁移软链接不得跟随到 T1 扫描，也不再计作本机占用。执行前称“预计释放”，执行后报告内置盘可用空间实测变化，并说明 APFS 共享空间只能估算的部分。

## Scope

### 默认只扫描本机内置磁盘

- 默认排除 `~/Library/Mobile Documents` 和 `~/Library/CloudStorage` 云同步目录，即使文件已经缓存在本机也不读取或计入本机扫描。范围外的绝对路径引用原样保留，不阻断本地 worktree 搬移；组内无法解析的引用仍须明确列出并阻止该组。
- 已迁移到 T1 的旧路径软链接是访问入口，不纳入项目引用图，也不阻断其他 worktree。组内其他链接按原始目标逐条核对；绝对目标保持不变，相对目标在副本中重定位；只有目标语义无法保留时才阻断该组。虚拟机挂载或句柄别名未解析时仍保持未知。

- 默认只扫描本机内置磁盘上、当前任务范围内的数据。外接硬盘、移动盘、网络共享、其他机器及挂载的磁盘镜像均不纳入；只有用户明确指定对应磁盘或路径时，才能加入扫描范围。“全面扫描”“所有 Codex 数据”不构成扫描其他盘的授权。
- 扫描前以系统挂载信息和物理磁盘归属核实目标；路径看似在本机主目录内也不能直接视为内置盘。不能沿符号链接、别名、junction、嵌套挂载点或项目历史引用进入未经明确授权的其他盘。内置磁盘正常的 APFS 系统／数据卷按实际物理归属判断，不能只凭卷名、路径前缀或设备编号猜测。
- T1 上已有工作区、Git worktree、历史报告或备份，不代表允许扫描 T1。读取任务明确指定的 Skill 文件、代码或验收清单，不等于获准遍历所在磁盘；报告输出位置也不改变扫描范围。默认不检查其他盘的目录占用，不将其容量混入本机占用或可清理量。
- 遇到范围外的卷或引用，只记录“其他磁盘，按默认范围排除”，不递归读取，不计作本机漏扫或零占用。用户另行明确授权后，仅扫描指定范围，并与本机统计分开汇报。

### 本机逻辑大小与外置链接目标必须分账

- “本机逻辑大小”只统计所选范围内、实际存放在本机内置磁盘上的普通文件：按文件身份（设备号与 inode；Windows 使用卷与文件 ID）去重后，将每个文件的逻辑长度相加。硬链接的多个路径只代表同一份文件数据，只计一次；父目录与子目录汇总不得再次相加。稀疏文件按逻辑长度统计，并同时说明它的文件系统分配量可能更小。
- 遍历目录和读取文件属性时不得跟随软链接、macOS alias、Windows junction/reparse point 或其他重解析点。软链接只登记链接路径、原始目标、目标是否存在及目标所属卷；链接目标中的文件大小不能加入本机逻辑大小。若目标位于 T1 等外置盘，默认不遍历目标内容，也不估算整盘大小。用户明确指定目标路径并授权检查后，才可测量该精确目标，并将结果放在独立的“外置链接目标”小计中，绝不并入本机总数或本机可释放量。
- 本机所选范围之外的链接目标，即使指回本机其他目录，也不算在当前范围内；若目标本身另行包含在扫描范围中，只按目标文件身份计一次。不得因为发现一个链接就扩大到其父目录、目标卷或整盘。
- 报告至少分开写“本机逻辑文件大小（普通文件 st_size 合计）”“本机文件分配量（文件系统分配字节）”和“外置链接目标大小（如获准测量，单独列出）”。逻辑大小说明文件内容量，分配量说明文件系统报告的占用，两者都不能直接当成删除后可释放空间；APFS 克隆、快照、压缩和稀疏文件会使实际释放量不同，执行后以本机可用空间的实测变化核验。禁止使用会解引用链接的目录大小结果作为本机总数，也禁止把本机与 T1 的数字相加后称为“本机占用”。

全面发现与来源判断独立：全局状态使用明确适配器与字段白名单，不读取工作树任意同名配置或会话正文。测试批次由运行内容证据确认，配置/依赖/夹具及未识别候选单独报告。历史缺失与范围外引用保留提示，不混同真实读取失败；覆盖报告同时列分阶段状态、原始事件、唯一诊断与唯一路径。详见 SOP §7.3。

- Confirm the current execution account and home from the operating system account database, then inspect only that account. Do not scan or modify other accounts merely because they are readable. Record the platform, account, home, confirmed Codex roots, ownership, permissions, and root-level access gaps.
- Inspect fixed Codex roots plus exact project/task roots tied to supported Codex state or session metadata. Use `Documents/Codex` and `Documents/ChatGPT` only for limited-depth entry discovery; recurse only into confirmed projects. Never treat Documents, Downloads, Library, the user home, C:\Users, or a disk as a Codex root.
- Include archived or demonstrably closed sessions, Codex caches, logs, temporary files, and old complete regenerable artifacts inside confirmed Codex worktrees or Codex-created Documents workspaces. Keep workspace/worktree roots, source, Git metadata, and user outputs protected from direct deletion; a separately qualified complete worktree may be moved intact to T1.
- Use provenance, ownership, active-process/open-handle checks, Git status, configuration/metadata, and content inspection. Age, size, or a name such as cache, build, or dist is not enough.

## Broad discovery and attribution contract

The default full scan means every confirmed Codex root in the current account,
not the account's whole home. It includes the Codex state/data directory, supported
Codex application data paths, and these exact macOS client paths when present:
`Library/Caches/Codex`, `Library/Caches/com.openai.codex/org.sparkle-project.Sparkle/Installation`,
and `Library/Logs/com.openai.codex`. These entries do not authorize scanning other
children of `Library/Caches` or `Library/Logs`; cache and log deletion must use
their dedicated process, handle, date, ownership, and volume checks. It also
includes exact project roots named by supported Codex state
or session metadata, linked worktrees registered by those projects, and task
runtime paths supported by source or configuration evidence. `Documents/Codex`
and `Documents/ChatGPT` may be checked only to discover project entries at a
limited depth; the scanner recurses into an exact project only after it confirms
Codex provenance. A session `cwd` never makes its parent container a scan root.
The scanner does not recurse through home, Documents, Library, cloud storage,
other accounts, external volumes, or nested mounts. Every confirmed root records
its source evidence; excluded paths, permission errors, timeouts, interruptions,
and cross-volume boundaries are reported as excluded or unknown, never as zero.

Project identity is evidence-based: Git common directories and normalized remotes,
explicit Codex workspace/state paths, manifests, generated configuration and
cross-directory references may associate an item. Similar names, dates, versions,
or batch labels only create a low-confidence association and never merge projects.
An item may belong to a project without being replaceable by another result in that
project. Test runs therefore carry inputs, model copies, intermediate files,
reports/databases, completion status and explicit dependencies; an incomplete new
run cannot replace a completed older run.

The same per-run inventory records files, directories, links, file identity,
logical bytes, allocated bytes, modification times, and read errors. Candidate
sizes, file counts, worktree file activity, and static reference discovery reuse
that inventory. It must not follow symbolic links or add linked-target bytes to
a local total; linked T1 paths are aliases only. The complete scan has a shared
1200-second deadline, including bounded external commands. A timeout or
incomplete source/root discovery blocks the cleanup phase.
SHA-256 confirmation is required for content duplicates; APFS clone/snapshot
sharing remains physically unknown. Virtual-machine and container packages or
disks (including sparse images, parent/differencing disks and snapshot metadata)
are reported with read-only dependency, process and mount status. A running,
mounted, or status-unknown image is not counted in confirmed duplicate bytes, and
an image byte match never claims guest-filesystem equivalence. All broad-discovery
records have an empty `trash_paths`; they are review evidence only.

### Runtime data and directory ledger

Task runtime data outside a worktree is included only when a supported Codex
state/configuration path names that exact location and its source or configuration
confirms the association. A product name, prior project mention, or generic
Library location is not enough. Shared Frida, uv, npm, Cargo, model and plugin
stores remain shared dependencies; they are not made Codex-exclusive by name.

The same inventory feeds a non-overlapping `directory_summary` inside the
confirmed Codex roots and linked project roots. It does not create summary rows
for home-level or generic Library directories. Each row reports file and hard-link path counts, logical and
allocated bytes, source/origin state, association status, purpose, coverage and a suggested
disposition. The structured `disposition_class` is one of `本地保留`, `T1 工作数据`,
`归档候选`, `可再生清理候选` or `暂不处理`; `activity_status`, `retention_note`
and `recovery_cost` keep unverified activity and restoration impact explicit. When
activity has not been checked, the effective class remains `暂不处理`; a planned
route is shown separately and never grants an action. The summary is a reporting
ledger only: every row has an empty `trash_paths`, and the
100 MB large-file threshold never suppresses a directory whose accumulated files
are large.

When a current runtime directory is identified only by a fixed application
identifier/path mapping, the row is explicitly `association_status: provisional`
and `evidence_status: mapped-only`; the missing source/configuration evidence is
shown in the reports and the row is not treated as confirmed provenance or idle.
`directory_summary` and the top-level usage total follow the local-only accounting
rule above. A symlink row describes a reference, not the size of its target.

The full-discovery invocation confirms the current account from the system account
database, scans every confirmed Codex root, and excludes its report directory:

```sh
python3 scripts/scan_codex.py \
  --workspace <scratch-workspace> --home /Users/mac \
  --scan-mode full
```

`--root` narrows this to a validated subdirectory of an already confirmed root
and is reported as a subset; it cannot add an unconfirmed directory. The shared
scan budget is 1200 seconds. A run over budget or with incomplete coverage cannot
be described as a successful full scan and cannot proceed to cleanup.

T1/T1 remains only the designated backup destination under its separate vault
procedure. New verified snapshots use
`/Volumes/T1/Agent/archive/storage-observatory/snapshots`; the existing
`/Volumes/T1/codex/storage-vault/snapshots` remains readable and restorable.
The scanner never moves old snapshots or treats an existing T1 directory as
migration verification. Existing T1 contents are not local occupancy and are
never folded into the current machine's reclaimable total.

## 每日只读健康检查

对真实检查缺口继续做用途分析：复用项目、批次身份、计数、输入/结果和路径引用；对空文件、损坏记录和大文件读取有限头尾样本，对读取被打断的目录重试查看直属成员。报告用途、证据强度、保留/核实建议及尚缺信息。容量遍历先完整结束；用途分析按目标接续，默认总预算 120 秒、单目标 5 秒、最多 4 个并行目标，已完成结果和未检查项都保留。一个阻塞目标不能占满全部检查机会；不输出文件原文，不跟随链接或跨卷。用途查明不能增加删除权限。每日摘要及历史保留容量、分析结果、目录级精简统计和耗时，详细证据放在报告诊断区。覆盖变化单独标为“新增覆盖”或“覆盖变化”，不伪装成从零增长；旧摘要缺少目录字段时显示未记录。

首次手动调用本 Skill 时，先通过 Codex 产品自动化入口检查当前项目是否已有每日北京时间 09:00 的存储检查任务。若已有匹配任务就复用；只有提示内容过期时才更新该任务，并保留原有时间、项目、模型、推理强度、状态和本地运行设置。缺少任务时才创建，不得重复创建。创建和更新都必须使用 Codex 自动化管理入口，不能编辑 `automation.toml`、launchd 或 crontab 代替。

每日自动化提示只负责调用本 Skill 的每日入口并展示返回的 `chat_report`；扫描范围、覆盖验收、报告格式和只读边界都以本 Skill 为准。每日运行失败或扫描不完整时，只报告失败/部分结果，不创建或更新自动化，也不把占位 0 当成无候选。当前宿主若没有可用的产品自动化入口，说明阻塞原因和解除条件。

使用独立包入口：`python3 scripts/daily_codex_health.py --home "$HOME"`。每日只遍历当前执行账号内已确认的 Codex 根，排除整个 home、其他账号、iCloud 和外置卷；完整扫描预算为 1200 秒，并复用本轮文件清单。完整内容重复校验可另外使用 `scan_codex.py --scan-mode full --duplicate-hash`，不能把日报当成删除授权。

默认工作目录为 `/Volumes/T1/Agent/work/codex-storage-cleanup/daily`，明细和报告使用两个固定暂存槽，全部成功后才切换摘要指向；失败不覆盖上次成功摘要、报告或证据。同目录并发检查跳过，不争抢输出。只保存最近 30 次生成的摘要，不保存百万文件原始清单。仅替换检查器自己的生成报告，不清理用户文件或旧验收目录。扫描阶段共享 1200 秒预算，报告收尾使用其剩余时间；超时终止本轮独立进程组（包括报告子进程）。如果容量 JSON 已经写出，失败记录仍展示已测容量和部分大白话报告，同时保留上一份成功摘要；其余未知/失败不补零或冒充本次完成。

每日任务只读，不开启服务或窗口，不删除、移动用户数据，不挂载、启动或转换镜像，不操作 T1。报告可用空间、占用变化、已验证旧构建候选、阶段状态和真实缺口。来源未知、未完成/活动批次、会话图片、依赖、模型、镜像和数据库均保留。新增分析项仍为 `discovery_only`、空 `trash_paths`。用户说“自动清理”但实际只要求“每日定期检查”时，按此只读流程执行；只有明确运行默认清理入口时才执行三类策略。

读取、进程和句柄检查超时必须保留未知状态；不可中断的系统子进程不得拖住扫描调用方。报告每阶段及整体耗时。未指定通知偏好时，仅在明显占用增长、新清理候选、低空间阈值变化、新失败或需用户操作时通知；无变化或同一阻塞不反复通知。

## Authorization and safety rules

The verified worktree relocation above is an explicit exception to local-root preservation wording below: preserve all source and working data on T1 and the old-path entry point, not a second full local copy. Root protection still prohibits discarding a worktree as regenerable cache.

- Separate discovery, candidate reporting, authorization, action, and verification. Inspection, backup, and planning remain read-only; `apply_cleanup.py --apply` is the explicit action boundary for the three default groups.
- The default action scope is fixed: verified regenerable caches, compiler/intermediate outputs and redundant complete builds may be permanently deleted without a backup; closed, independently evidenced user-data paths are removed only after a verified T1 snapshot; only associated worktree groups idle for more than 168 continuous hours with all activity, handle, reference, and Git checks passing are moved to T1. A finalization marker never overrides recent or unknown activity. Never expand an item to its parent workspace or worktree root.
- Do not use Trash/Recycle Bin for the default direct-delete group because it does not reliably release space. User data, visualizations, outputs and anything outside the three groups remains review-only unless a specific closed-task path has completion, retention and no-reference evidence.
- For another user, inspect only what the OS permits; do not use elevation or permissions changes merely to bypass uncertainty. Report inaccessible profiles and stop on protected or ambiguous data.
- Treat workspace/worktree roots, active sessions, running tasks, open files, source code, user documents, settings, credentials, databases, lock files, and system snapshots as protected from direct deletion. Uncommitted or unknown project data is also protected unless its complete worktree is independently qualified for an intact long-idle T1 migration.
- Never empty Trash/Recycle Bin, delete APFS/Time Machine/Windows recovery data, or use broad recursive deletion against unresolved paths.
- A request to merge or edit this skill, scan, back up, or ask about recoverable space is not disposal authorization. Neither a script allowlist nor an earlier recommendation authorizes a new path. Revalidate the exact scope and method before action.

## Required workflow

1. Discover users and platform-specific Codex roots, resolve absolute paths, and reject symlinks, aliases, junctions, and reparse points for destructive actions.
2. Build a candidate ledger with user/platform, exact path, Codex provenance, type, size, time, active/open state, Git state, risk, recovery path, proposed action, priority/reason, retained latest path, replacement evidence, rebuild command, network cost, and rebuild time.
3. Apply the old-artifact-first recommendation and latest-usable retention policy, then classify each item as protected, regenerable, high-risk user data, or unknown/system. Confirm the parent workspace/worktree provenance, but propose only precise child artifacts; never propose deleting the workspace/worktree root.
4. Back up and content-verify archived/closed sessions before deleting only the files older than seven days; also allow an independent closed-task output only when its completion marker, no-reference evidence and inactivity are revalidated. Do not touch recent archives, ordinary sessions or mixed/unknown outputs.
5. When the user requests the default cleanup, run the bundled executor with `--apply`; it revalidates exact paths immediately before action, moves only associated worktree groups idle for more than 168 hours after every safety check passes, and skips any item whose state changed. Finalization alone never overrides recent or unknown activity.
6. Verify the result per user and category, confirm that unapproved data and source state are unchanged, calculate actual space change, and report skipped or inaccessible items.

## Candidate-specific rules

- For archives and closed task outputs, compare exact path/file counts, total bytes and content checksums; accept both `.jsonl` and `.jsonl.zst`, exclude filesystem metadata sidecars from real-chat counts, and select only archive files or independent output paths whose activity and retention evidence passes the seven-day rule.
- For caches, logs, and temporary files, confirm Codex ownership, non-critical content, no active use, and regeneration before proposing permanent deletion.
- For artifacts inside Documents workspaces, require strong Codex provenance for both the parent and child path, no active use, and path-level confirmation. Preserve source, user documents, and the workspace root; do not require a clean Git tree to delete a separately verified generated artifact, but never delete mixed or ambiguous content.
- For worktrees and build artifacts, group by user/project, retain the latest completed build directory, and remove complete confirmed older build directories only; move a finalized worktree only when its whole group has also been inactive for more than 168 hours and every handle, activity, reference, and Git check passes. A finalization marker never overrides recent or unknown activity. Classify every path reference: repair in-group paths, preserve external absolute paths, and rebase external relative paths in the T1 copy. Old-path symlinks to verified T1 worktrees are access aliases, not project references or blockers. Preserve dirty/untracked/ignored content and Git registration; never hand-delete Git objects.
- Treat `visualizations`, task `outputs`, unique exports, and recent/ordinary conversations as user data. A specific closed output can enter backup-then-delete only with a completion marker, no supported reference and more than seven days of inactivity; otherwise keep it. For T1 offload or restore, follow [the vault reference](references/t1-vault-operations.md): verify the designated volume, snapshot and content digest, explain path availability after offload, and remove the verified local copy only as part of that scoped action.

## Report presentation

### 先调查方法，获授权后才改程序

用户要求“想办法”“查原因”“如何归类”时，先进行只读调查：检查现有清单、任务记录、上级目录、文件名、包结构及必要的有限内容样本，在对话框说明方法、实测结果和仍仅属推断的部分。这些请求不授权修改扫描器、测试、配置或执行清理。只有用户明确要求实施或修改时才改相应内容；“把方法写入 Skill”只授权更新技能说明，不自动授权修改程序。不要以改变显示标签代替查明用途。

### 分类必须按原始字节对账

复用同一份扫描清单和相同的文件身份去重规则；每个实体只计一次，父子目录不能重复相加。逐项记录归属、用途、原始字节数、判断依据以及内容证据或上下文推断。分类合计必须等于原扫描相同范围的原始字节数，再统一换算展示单位；不能靠漏项、补零或四舍五入凑平。明确扫描日期，历史数据复核不能称为当前重新扫描。字节对账通过只说明容量没有漏算或重复计算，不代表所有用途都已得到内容验证；仅凭目录和名称推断的部分要在对话中明确说明，并继续对重要项补证。

### 自主查账，不反复询问

在已经授权的只读范围内自行完成调查，不反复问“是否继续”“要不要查”“属于哪个项目”，不把能够通过文件和上下文查清的问题交回用户。固定顺序：从原清单找回精确文件实体与字节数 → 按实际位置和任务归组 → 查上级目录、任务记录、配套源码及组件清单 → 检查文件头、压缩包目录、数据结构或有限内容样本 → 解释是什么、为什么产生、用途及证据 → 按原始字节对账。对仍只有泛化名称的项继续补证，不以改标签、隐藏小项或凑齐总数结案。检查程序只读其源码或格式，不运行被调查的工具。

遇到权限失败、文件已消失或变化，先尝试已有清单、历史记录和相邻证据等只读途径，再如实说明实际限制；不得伪造内容验证。只有确实需要新增授权、用户独有信息或改变任务范围时才集中提问。自主调查不授权修改程序、执行修复、安装、移动或删除。

### 必须包含按位置或任务的版本

每次查账汇报必须先给用户偏好的“位置／任务版”，不能只给文件类型版。表前先说“这 X 的主要组成如下，数据来自某月某日的验收，并非今天重新扫描”，或明确本次实际扫描时间和范围。说明是全部占用还是此前某一子集，不能把子集容量冒充目录总占用。

固定表格列为「位置或任务｜占用｜具体是什么、为什么产生」，必要时增加「判断依据」。保留可辨认的目录名或任务名，例如 `.codex`、安装包修改任务、媒体备份任务，并解释其含义；不能全部替换成抽象的“数据库／工具／资料”等类型。使用准确、互不重叠的归组边界，同一任务的工作目录与输出可合并，但须说明口径变化。小项可按有明确用途的任务组汇总，不使用“未识别”兜底，不用文件链接承载解释。

可追加“用途分类版”帮助比较，但位置／任务版必须保留且排在前面；两个版本是同一份数据的不同视角，不能相加。最后在对话中简述原始字节是否对平、已核实的证据与必要推断、本轮实际动作。没有新扫描或前后比较时，不强行输出空间变化表。本节优先于下文旧报告顺序。

### 永远在对话框内汇报

本 Skill 的结果一律直接写在当前对话框，包括结论、方法、分类明细及容量、对账结果、推断依据、验证结果、实际改动和剩余问题。内容较多时在对话中按用途分组展开，不把汇报转交给文件。禁止用“查看报告”“详见文件”等外部文件或网页链接替代汇报，也不以附件、Markdown、HTML 或 JSON 文件作为最终交付方式。工具生成的文件只作为内部核查资料；除非用户另行明确索要文件，不提供报告文件链接，不要求用户离开对话框查看结果。这条要求优先于下文的可视化或文件报告说明。

### 每项都给出用途归类

不以“未识别”“待识别”“项目暂未标注”作为最终用途分类。先查已有项目身份和任务路径，再结合上级目录、文件名、扩展名、包结构与有限内容样本判断：共享数据库、会话、图片、独立任务成果、备份、依赖、构建等分别列出。没有 Git 身份的任务使用完整工作目录区分，不能把同名任务合并。依赖包归所属任务或工具，不要求每个包都有项目编号。

调查结果分别记录用途、所属容器、判断依据与证据强度，不改写真实 `project_key`、来源、读取状态和删除权限。目录及格式推断必须明说。仅能给出容器与格式的低具体度项，应继续检查占用最大的项的目录成员、文件头或来源记录，补足具体用途，不能只换掉标签就声称调查结束。实际权限失败、容量没测到或内容没读过仍须如实保留。

具体执行 [SOP §7.4 的只读查账流程](references/codex-storage-cleanup-sop.md)：精确找回文件实体，检查全部目标的可读性及格式，再按内容、组件清单和来源代码补证，最后核对原始字节。复核历史清单不重测全部磁盘、不覆盖原验收；临时分析只在内存中运行，不修改或执行被调查的程序。该方法不依赖额外安装或未提交的归类脚本。归类完整不等于可以清理，尤其保留备份、会话、图片、数据库与独有成果。

Always report the findings, evidence and verification directly in the current Codex conversation. Do not substitute a report file, attachment or external link for the answer. Generated HTML/JSON/Markdown is internal evidence only unless the user explicitly requests a file.

### 存储检查报告格式

日常检查与手动报告均遵循 SOP §11.1：容量、增减量、耗时及百分比保留两位小数，每个测量数字后直接带单位（如 `67.34 GB`、`减少 20.26 GB`、`331.11 秒`）；不能只在表头声明单位。时间单独标为 `11:18`，与容量分列。聊天用 🔴 标出新增占用或可用空间下降，🟢 标出占用减少或可用空间增加；支持颜色的报告用红/绿表达同样的含义，并保留文字说明。

每份日报和手动检查报告固定输出三张表：①空间变化；②增长来源与已知占用；③清理建议。第三张表逐项列出每个有单项证据支持的候选，包含精确路径、单项占用、建议类别和判断依据；不得把多个路径合并成“其他”。表内按「建议安全清理」「先备份再删」「暂不处理 / 搬移」分别计算小计，并给出候选总量；「保留」内容可以作为非候选明细列出，但不计入候选总量。按文件身份去重，父目录与子项不得重复计算。

只有扫描完整并通过验收，且逐项清单确认没有候选时，才能写候选总量 `0`。扫描未完成时，将有证据的条目标为“部分清单”，列出已确认小计，并把整体候选总量写为“未知”；没有逐项候选证据时也写“未知”，不得把占位 `0` 解释成无候选。未通过完整验收的扫描不沿用旧扫描候选。候选占用是对象的逻辑大小，不承诺实际释放同额空间。

名称必须解释对象是什么、为什么产生；路径使用有含义的链接标签。增长组成不足以对账时，单列尚未定位的量、不可比较的覆盖和下一步检查，不能将逻辑量或分配量当作实际释放量。明显增长独立触发提醒，不必等到低空间警戒线；具体口径、证据和授权要求见 SOP §11.1。

Report only measured amounts. If an optional “all builds removed” scenario is shown, label it as an alternative estimate outside the confirmed-candidate total; it must not broaden the default action scope or imply that keepers are approved for removal. Exclude known in-use paths from immediately reclaimable bytes and mark unknown usage as unknown. Label the scan time when reusing an earlier result. Do not invent byte counts for unmeasured download caches, sessions, or images.

Treat colloquial “会话/绘画缓存” carefully: distinguish chat history, generated image originals, and confirmed regenerable intermediates. Never call chat history or unique generated images disposable cache. Never substitute small caches for completing the large-build assessment.

The standalone report keeps the established Lieflat Charts Wire black/gray base, green/orange change semantics, 2×2 chart arrangement, and cleanup-specific dimensions such as user, platform, artifact type, risk, provenance, recoverability, and exact path. Its CSS is bundled in `scripts/report_theme.py`; generating an HTML report does not read a parent Skill at runtime.

The chat report lists every confirmed candidate path as its own row; it never hides small candidates in an “other” group. A standalone HTML ledger may use progressive disclosure, but every exact path, per-item size, category, and evidence record must remain available when expanded. Expanding a group must never widen the cleanup scope.

## Completion report

Report all inspected users and platforms, discovered roots, candidate counts and sizes by category, exact artifact paths/actions for anything moved or deleted, backup and checksum results, actual space released, inaccessible/skipped items and reasons, and explicit confirmation that workspace/worktree roots, active sessions, unapproved user data, source/Git state, credentials, settings, Trash/Recycle Bin contents, and system recovery data were preserved.

## 报告运行入口

For a visual audit, run the bundled read-only scanner and child report builder:

```sh
CHILD_SKILL_ROOT=/path/to/codex-storage-cleanup
python3 "$CHILD_SKILL_ROOT/scripts/scan_codex.py" --workspace <scratch-workspace>
python3 "$CHILD_SKILL_ROOT/scripts/serve_codex_report.py" --workspace <scratch-workspace>
```

The scanner writes `work/storage-analysis-live.json` and the builder writes `outputs/codex-storage-cleanup-report.html`. The report bundles its own visual tokens and keeps the main conversation summary focused on Codex total usage, location and project breakdown. Detailed paths, diagnostics, and authorization state remain in the HTML diagnostic area. The child server uses a fresh local token and an allowlist derived from the ledger, supports only exact `open` and reversible `trash` actions, and never acts during scanning or report generation.

To apply the default policy after a fresh scoped rescan:

```sh
python3 "$CHILD_SKILL_ROOT/scripts/apply_cleanup.py" \
  --home "$HOME" --apply
```

The executor permanently removes only exact regenerable paths with fresh source/input evidence, uses `vault.py backup` plus archive or generic `user-data` offload for qualified old sessions/outputs, and moves only associated worktree groups idle for more than 168 hours after all checks pass to the verified T1 worktree area; a finalization marker never overrides recent or unknown activity while repairing references/Git registration and replacing local directories with symlinks. It prints exact actions, T1 snapshot IDs, skipped paths, reasons that blocked old worktree groups, capacity de-duplication evidence and measured free-space change. The daily health entry remains read-only. Vault paths resolve from the current execution account; the executor refuses a requested home that differs from that account's home.
